# Reusable Composer analysis for large workspaces

The new `indexed-v1` mode is opt-in. The current legacy and schema-3 scoped map
formats remain available with their existing defaults. Existing saved configuration
files continue to load. An old map must be regenerated to gain the indexed Java graph.

## Create or reuse a map

In `run.cmd` or `run-verbose.cmd`, choose **Create a new config → Composer map →
Create a new map → New map analysis → Reusable AST index for large workspaces**.
Enter a stable workspace ID. Review and save the configuration; saving does not
start mapping. Start a new migration when ready.

The mapper always maps the workspace globally. The converter's selected channels
and operations restrict subsequent inventory loading, Java dependencies, reports
and imported note bodies. Required called-operation contexts are included too.

To reuse a completed indexed map, choose **Use an existing map folder**. The wizard
detects the format and workspace ID from the small descriptor. It does not traverse
the map while creating the configuration. Migration intake validates the generation,
checks source fingerprints, selects the dependency closure and pins that generation
in the run database. A validation receipt lives under `<output_root>/.map-validation`;
subsequent runs using that same immutable generation avoid hashing every note again.
For a map just generated by the converter, the mapper's write-time digests provide
that receipt after database and link checks; intake does not reread its entire fresh
output. A previously supplied map gets a full initial note validation.
Selected note bodies are still checked whenever imported. Treat published maps as
immutable; regenerate into another folder after source changes.

Equivalent YAML settings:

```yaml
source_root: ../huge-bank-demo/composer/Workspace
source_workspace_id: huge-bank-demo
mapper_jar: ../source/composer-mapper/target/composer-mapper-1.1.1-jar-with-dependencies.jar
mapper_vault_layout: scoped
mapper_analysis_format: indexed-v1
output_root: ../work/migration_runs
channels: [INTERNET]
include_operations: [GetClientOverviewOpHuge00001]
java_scan_inactivity_timeout_seconds: 900
mapper_analysis:
  heap_mib: 768
  batch_files: 100
  batch_mib: 4
  java_file_mib: 8
  sqlite_cache_mib: 32
```

For an existing map, add `existing_composer_map: ../maps/huge-bank-v1`.
For a fresh generation reusing previous file analyses, use
`mapper_analysis_reuse: ../maps/huge-bank-v1` instead. Relative paths in a saved
configuration are resolved relative to its YAML file. Existing-map selection never
rewrites the source map. Rebuilding with cached facts reconstructs consuming-context
records in a fresh destination. Finalized notes whose bytes are identical are copied
from the previous map with a streaming digest check; changed notes are written anew.
The descriptor and progress log report the reused note count. Files are never hard linked.

## Build and standalone usage

Set `JAVA_HOME` and `PATH` to JDK 25, then build from the repository root:

```powershell
mvn -f source/pom.xml package
```

After dependencies are cached, `mvn -o -f source/pom.xml package` builds offline.
The reactor builds the shared analyzer before the mapper; building only the mapper
POM requires the sibling artifact to be installed first. The mapper's CMD wrapper
uses the reactor. The resulting fat JAR includes the analyzer, SQLite JDBC and JSON
reader. At mapping time it needs JDK 25, the sources and writable local disk; Python,
Maven, an AI model and internet access are not required.

```powershell
java -Xmx768m -jar source/composer-mapper/target/composer-mapper-1.1.1-jar-with-dependencies.jar --root C:\code\composer --vault C:\maps\bank-v1 --vault-layout scoped --workspace-id bank --md true --analysis-format indexed-v1
```

Generate an updated map into a **new** destination:

```powershell
java -Xmx768m -jar source/composer-mapper/target/composer-mapper-1.1.1-jar-with-dependencies.jar --root C:\code\composer --vault C:\maps\bank-v2 --vault-layout scoped --workspace-id bank --md true --analysis-format indexed-v1 --reuse-analysis C:\maps\bank-v1
```

After an interrupted or failed build, `--resume-analysis C:\maps\failed-builder`
reuses only compatible, completed file facts into a fresh destination. It never
publishes partially analyzed files or updates a live map in place. Choose either
`--reuse-analysis` or `--resume-analysis`, not both.

Unchanged files need no AST/XML parse. Changed Java files are parsed again.
Unchanged callers can reuse resolved edges while the symbol/visibility policy
matches. Declaration or project-visibility changes conservatively re-resolve stored
reference facts; they do not require reparsing unchanged sources. Analyzer/JDK
changes invalidate incompatible parse facts. Source additions, deletions and byte
changes during publication or intake reject a mixed snapshot.

## Storage and memory boundaries

The map keeps readable canonical Markdown plus a small `vault-manifest.json`
descriptor and `analysis/analysis.sqlite`. Ship them together. The descriptor has no
project-wide entity, context, consumer or dependency arrays. It records the schema,
workspace, database digest, capabilities, analyzer policies, producer JDK and budgets.
The SQLite database is checkpointed and closed before atomic descriptor publication;
the finished map does not depend on a separate WAL file.

| Stored relations | Purpose |
|---|---|
| `files`, `revision` | Raw hashes, encoding, completion and policy evidence |
| `java_classes`, `java_facts`, `java_sources` | Ordered AST metadata/reference facts and source ownership |
| `java_projects`, `java_roots`, `java_project_refs` | Declared project visibility and source roots |
| `java_edges`, `java_resolution_ready` | Resolved source-reference sites and completed caller analyses |
| `xml_nodes`, `xml_attributes`, `definitions` | Ordered XML/INI structure, source occurrences and selectors |
| `channel_mappings`, `channel_imports` | Original global inventory binding policy |
| `context_mappings`, `context_imports`, `context_java_roots` | Actual consuming-channel bindings, implicit XML base and Java roots |
| `canonical_definitions`, `configured_counts`, `operation_roots` | Original consumer identities and compact global multiplicities |
| `operation_context_index`, `context_parts`, `context_calls`, `context_bindings` | Qualified execution contexts, ordered child records and call links |
| `notes`, `note_consumers`, `records` | Canonical note identity/digests, sharing joins and diagnostics |

Outgoing/incoming edge indexes and keyed XML/context lookups serve recursive SQL
traversal. The converter uses temporary selected-context, selected-definition and
selected-Java tables. It does not rebuild a global syntax dictionary or expand every
operation into all Java reference sites. Global consumer/root factors preserve
distinct operation/channel counts and reference multiplicity, including repeated
references, diamond paths and the existing cycle policy. Imported execution aliases
do not become extra original consumers.

One shared `JavacTask` parse extracts reference facts and the mapper's class metadata
from each captured source revision. The converter's old-map scanner uses the same
analyzer and resolver through compatibility adapters. No annotation processors or
workspace-wide compiler attribution run. Dynamic dispatch/reflection remain outside
this static graph. UTF-8, BOM handling and Windows-1255 fallback preserve raw hashes.
Empty and comment-only Java files do not become implementations.

XML/INI uses secure streaming facts and SQL-backed node views. External DTD/schema
resources and entities are never fetched. Ordered attributes, text/CDATA, namespaces,
selectors, overrides, `onlyFor`, repeated step labels and routing evidence retain their
existing meanings. Individual business-model fragments have explicit limits; splitting
the global store does not imply that an arbitrarily large individual operation fits.

| Resource | Default / bound |
|---|---|
| Mapper heap | 768 MiB; YAML allows 128–4096 MiB |
| Compiler batch | At most 100 files and 4 MiB estimated decoded text; one worker |
| Individual Java input | 8 MiB; a file larger than the batch runs alone |
| Mapper SQLite cache | 32 MiB; work tables/sorts spill to disk |
| Converter reader SQLite cache | 8 MiB per reader |
| Transactions | 500 writes or 4 MiB estimated payload |
| Query pages | 250 rows / 4 MiB; bounded lookup guards |
| Note, context or materialized XML/Java record | 4 MiB; oversized fragments fail explicitly |
| XML nesting | 512 levels |
| Shared Java metadata cache | 64 entries / 8 MiB estimated; no live AST cache |

Mapper tuning flags are `--analysis-batch-files`, `--analysis-batch-mib`,
`--analysis-java-file-mib` and `--analysis-sqlite-cache-mib`. Settings can lower the
tested upper bounds; they cannot silently enable unbounded batches. Compiler ASTs,
JVM/native allocations and operating-system caches consume additional memory beyond
source bytes or SQLite cache sizes. The heap is not a process RSS limit.

## Logs, reports and resume

The migration creates its run/log folders before indexed validation starts.
`logs/intake.log` and `logs/intake-progress.json` cover mapping, validation and
selected inventory. Mapper output streams to `logs/mapper.log`; the mapper also
maintains its own progress log in the map. Heartbeats show phase and last completed
work. A heartbeat does not count as scanner activity: real output or work-file
changes reset the configured inactivity timeout.

The intake reports contain selected implementation/dependency/use details plus
global diagnostics and exact global usage summaries for selected targets. Source
index reports explicitly identify their selected scope. Resume pins map digest,
workspace and selection; stale or replaced evidence requires a fresh intake.
Schema-4 runs retain the existing scoped conversion acceptance gates. This feature
does not enable conversion stages that were previously gated.

Both Excel entry points understand indexed maps. They spool connections and
dependency ordering to SQLite and write XLSX rows incrementally with `openpyxl`.
They do not construct a whole-project JSON payload. A prerequisite list exceeding
Excel's cell capacity requires `--include-relationships`, which retains the full
relationship rows. The original schema-2/3 export route remains available.

## Validation and rollout

Acceptance coverage includes real JDK/fat-JAR mapping, Bank Demo canonical-note and
context parity, static-edge/policy comparisons, selected-only intake and resume,
exact library decisions, cached file analyses, interrupted-build recovery, stale
source rejection, UTF-16/CDATA/namespaces, channel and format overrides, `onlyFor`,
a single XML document with hundreds of operations and 1,000 repeated steps, bounded
failure, and both workbook entry points.

The opt-in scale test is `source/tests/test_mapper_analysis_scaling.py`:

```powershell
$env:SNAPIR_REAL_SCALE_TEST='1'
.\.venv\Scripts\python.exe -B -m pytest source/tests/test_mapper_analysis_scaling.py -s -q -p no:cacheprovider
```

It generates 22,000 real Java files and 1,000 operations, maps under `-Xmx256m`,
then verifies a three-class selected closure and a helper shared by all 1,000
original operations. The test writes a local `measurements.json`. Set
`SNAPIR_SCALE_SOURCE` to reuse generated inputs, or `SNAPIR_SCALE_MAP` to benchmark
only an already completed, compatible map; reused mapping time is recorded as null.

An intermediate successful global run took 16m38s and produced a roughly 215 MiB
database. Removing a global incoming-edge scan and a commit per consumer reduced
the same map's selected inventory/count benchmark from about 299s to 21s, with
three implementations loaded and about 0.9 MiB of additional traced Python
allocations. These are local Windows measurements, not end-to-end conversion times
or total process-memory limits. Initial validation, source hashing, classpath/JDK
inventory, note import and report writing are separate work. The final run's
measurements and regression results are recorded below.

Final constrained-heap run: **22,000 Java files / 1,000 operations**, 24,000 entity
notes, **574.75s mapping** and **17.93s selected inventory/count processing**.
The selected closure contained three implementations; the leaf retained 1,000
operation consumers and 2,000 indirect references. Additional traced Python peak
allocations were 1.10 MiB; the database was 215.02 MiB. One mapper process-memory
observation reported a 213.41 MiB peak RSS. This is an OS measurement, not heap usage.
The mapper used JDK 26.0.1 on the local Windows 10 host; real startup tests also ran
with JDK 25 and compatibility scanner tests with JDK 21.

The complete scale test took 879.41s before the fresh-publication receipt change.
Much of the remaining time was the initial full note validation; a separate warm
validation took 81.68s. Fresh converter-generated maps now reuse their producer's
write-time note hashes. Existing external maps still undergo one full initial
validation, with progress, before their receipt is reused. Source fingerprint I/O
and selected note verification remain mandatory. See the
[recorded benchmark data](composer_analysis_benchmark.json).

Validation completed: 177 existing mapper/intake/Java regression tests; 100 indexed,
wizard and scoped-workflow tests (one pre-existing stale Bank Demo expectation
excluded); 13 JDK 21 compatibility tests; and the real 22,000-file scale test.
Offline Maven packaging passed. The publisher-receipt change has additional
startup and tampered-selected-note checks.

The actual `huge-bank-demo` overview migration also reached
`scoped_inventory_ready` with JDK 25 and a mock model: **280.03s** including a new
global map, followed by **15.29s** for a fresh migration reusing that map. Both
loaded exactly three operation contexts and 22 Java implementations for
`GetClientOverviewOpHuge00001`. The second run did not invoke the mapper. The
numeric progress adapter and scanner regressions passed a further 16-test check.

See the [changed-file inventory and reasons](composer_analysis_changes.md) for the
recovered source integrations, focused new modules, tests and documentation.

Keep indexed generation opt-in while gathering representative enterprise baselines.
The immutable existing-map path provides the main reuse benefit. Incremental map
rebuilds still evaluate final note content before checking its reuse digest;
automatic promotion of the default format remains separate rollout work.
